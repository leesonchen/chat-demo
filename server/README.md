# Chat Demo account and cloud backup service

The optional backend uses Node.js built-ins, including `node:sqlite`. It does not proxy DeepSeek chat requests. The browser continues to call the configured DeepSeek API directly.

## Register Chat Demo with the shared auth service

Register this app with the shared auth service. Give it an independent client ID and client secret, and register the exact callbacks `https://chat.example.com/api/auth/wechat/callback` and `https://chat.example.com/api/auth/qq/callback`. Set `allowQq` and `allowProfile` to `true` on that auth client to enable QQ login and profile retrieval.

## Configure the backend

Copy `server/.env.example` to `server/.env` and set:

- `APP_ORIGIN=https://chat.example.com`
- `AUTH_SERVICE_ORIGIN=https://auth.example.com`
- `AUTH_CLIENT_ID` and `AUTH_CLIENT_SECRET` from the shared auth service registration.
- `WECHAT_APP_ID` to the same Official Account AppID used by your existing Chat Demo accounts.
- `QQ_LOGIN_ENABLED=1` after configuring QQ in the shared auth service.
- `API_KEY_ENCRYPTION_KEY` to a 32-byte key generated by `openssl rand -base64 32`.
- `DATA_DIR` to a persistent directory.

Keep `server/.env`, the database, and backup files out of Git. Back up `API_KEY_ENCRYPTION_KEY` separately; losing it makes stored API keys unrecoverable.

## Run and reverse proxy

```sh
pnpm install --frozen-lockfile
pnpm build
pnpm server
```

The API listens on `127.0.0.1:8091`. Configure Nginx/Caddy to serve `dist/` on your site hostname and proxy `/api/` to `127.0.0.1:8091`. Keep the Node service bound to loopback and use HTTPS in production.

## QR login

Pages opened inside WeChat use the same Official Account to authorize the user and return to Chat Demo directly. Use a shared auth service that supports `mode=wechat_browser` and `/authorize/basic` for sign-in without profile access.

1. Click WeChat sign-in in Chat Demo to open the QR page on the shared auth service.
2. After scanning, the computer returns to Chat Demo with a one-time sign-in code.
3. Chat Demo verifies the browser's login state, exchanges the code using its client credentials and PKCE verifier, and starts its own session.

Chat Demo checks the returned AppID before matching the OpenID to an existing account. Its account details, API Key, and cloud backup are associated with that same account. Chat Demo saves the nickname and avatar supplied with an authorized sign-in and preserves existing profile details when the reply contains identity only.

## QQ web login and registration

Create a **website app** in [QQ Connect](https://connect.qq.com/) and wait for its review. Register the QQ platform callback as `https://<auth-service-host>/qq/callback`, then set `QQ_APP_ID` and `QQ_APP_KEY` on the shared auth service. Separately, register `https://<chat-demo-host>/api/auth/qq/callback` as the Chat Demo client callback in that service. These are two different callback URLs.

After setting `allowQq: true` and `allowProfile: true` in the auth client's `clients.json`, set `QQ_LOGIN_ENABLED=1` in Chat Demo's `.env` and restart both services. Users can then create or restore a QQ-based account from a normal web browser. QQ identity is separate from WeChat identity, so the service does not merge accounts by nickname or avatar. QQ Connect documents that website OAuth does not work in an app-embedded H5 view; use the system browser.

## Data and behavior

- SQLite database: `DATA_DIR/chat-demo.sqlite`.
- Cloud backups: `DATA_DIR/backups/`, one ZIP snapshot per user. A new export replaces that user's previous snapshot.
- Restoring a cloud backup replaces the current device's local history; it does not merge histories.
- The ZIP retains all conversation branches and locally available image originals. Other attachment types retain metadata only, matching the existing local ZIP behavior.
- API keys are encrypted at rest with AES-256-GCM. After login, the browser retrieves its own decrypted key over the authenticated HTTPS session so the existing direct-to-DeepSeek client continues to work.
- QQ account lookup uses both the QQ AppID and the user's OpenID.

Back up the SQLite database and the `backups` directory together. Back up the encryption key separately and securely.

## Cloud backup membership

Signed-in users can start a free calendar month of cloud backup membership from Settings → Data management. The trial starts immediately, expires automatically, and can be started again after it expires. Its effective expiration date is the later of the trial expiration and any existing paid membership expiration.

With `MEMBERSHIP_MODE=required`, an active membership is required to upload or restore a cloud snapshot. Expiration preserves the snapshot. `preview` and `off` allow backup and restore regardless of membership status. The default is `off`. Local chats and local ZIP actions remain available.

New purchases are paused. If previously placed WeChat orders are still settling, keep the existing `WECHAT_PAY_*` configuration so the service can verify payment notifications and order status. See the [Chinese guide](README.zh-CN.md#会员与支付).
