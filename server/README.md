# Chat Demo account and cloud backup service

The optional backend uses Node.js built-ins, including `node:sqlite`. It does not proxy DeepSeek chat requests. The browser continues to call the configured DeepSeek API directly.

## Production configuration

- Frontend/API origin: `https://deepseek.leeson.top`
- WeChat Official Account AppID: `wx1713b39983b65190`
- OAuth callback: `https://deepseek.leeson.top/api/auth/wechat/callback`
- OAuth scope: `snsapi_base`

This version uses the existing verified WeChat Official Account (service account). It does not require a WeChat Open Platform website application and does not use the old `wx1.leeson.top/wx` message-push endpoint. Do not change the existing Official Account message-push URL, token, EncodingAESKey, or IP allowlist for this login flow.

## WeChat preparation

1. In Official Account settings, configure `deepseek.leeson.top` as the Web Authorization Domain.
2. Keep the `MP_verify_xxx.txt` verification file accessible at the domain root. If the domain has already been verified, no repeat verification is needed.
3. Reuse the existing service-account AppSecret from its current secure configuration. Do not reset it just for this application; first check whether other live services still depend on it.
4. Configure HTTPS for the domain.

## Configure the backend

Copy `server/.env.example` to `server/.env` and set:

- `APP_ORIGIN=https://deepseek.leeson.top`
- `WECHAT_APP_ID=wx1713b39983b65190`
- `WECHAT_APP_SECRET` to the existing Official Account AppSecret.
- `WECHAT_REDIRECT_URI=https://deepseek.leeson.top/api/auth/wechat/callback`
- `API_KEY_ENCRYPTION_KEY` to a 32-byte key generated by `openssl rand -base64 32`.
- `DATA_DIR` to a persistent directory.

Keep `server/.env`, the database, and backup files out of Git. Back up `API_KEY_ENCRYPTION_KEY` separately; losing it makes stored API keys unrecoverable.

## Run and reverse proxy

```sh
pnpm install --frozen-lockfile
pnpm build
pnpm server
```

The API listens on `127.0.0.1:8091`. Configure Nginx/Caddy to serve `dist/` on `deepseek.leeson.top` and proxy `/api/` to `127.0.0.1:8091`. Keep the Node service bound to loopback and use HTTPS in production.

## QR login

1. The browser requests a short-lived login transaction.
2. The frontend renders a QR code containing the WeChat Official Account OAuth URL.
3. The phone scans it in WeChat. `snsapi_base` silently authorizes and returns an OpenID to the callback.
4. The computer polls with a separate one-time ticket and secret to claim its own HttpOnly login cookie.

The QR state, browser polling ticket, and polling secret are distinct. The transaction expires after ten minutes and can only be claimed once. `snsapi_base` returns OpenID, not nickname or avatar; new accounts initially display as “WeChat user”.

## Data and behavior

- SQLite database: `DATA_DIR/chat-demo.sqlite`.
- Cloud backups: `DATA_DIR/backups/`, one ZIP snapshot per user. A new export replaces that user's previous snapshot.
- Restoring a cloud backup replaces the current device's local history; it does not merge histories.
- The ZIP retains all conversation branches and locally available image originals. Other attachment types retain metadata only, matching the existing local ZIP behavior.
- API keys are encrypted at rest with AES-256-GCM. After login, the browser retrieves its own decrypted key over the authenticated HTTPS session so the existing direct-to-DeepSeek client continues to work.
- The provider-based identity table leaves room for a future QQ identity. QQ login, automatic sync, real-time multi-device collaboration, and conflict merging are not included in this phase.

Back up the SQLite database and the `backups` directory together. Back up the encryption key separately and securely.
